# DECISIONS — judgement calls made without asking

- Tests and the local mock run the **real** Edge Function handlers in Node 24 (native TS type stripping) against an in-memory DB, instead of a separate Python re-implementation in `scripts/mock_functions.py`, so the mock can never drift from production logic. The site repo's mock was not read (outside this folder). Mock lives at `scripts/mock_functions.mjs`.
- No supabase-js anywhere: functions talk to PostgREST and GoTrue with `fetch`, the SPA talks to GoTrue with `fetch`. Zero dependencies, nothing to bundle, nothing remote to import.
- One Edge Function per pane (12 total), each declaring its own role list per action inline. The shared `serve()` pipeline performs the check; `tests/matrix.ts` holds an independently written copy of the §8 matrix and the suite fails if they diverge.
- Unauthorised = one response for everything (no token, bad token, signed-in stranger, deactivated member): `403 not_authorised`. No hint whether the address exists.
- Revenue for non-owners: `bookings.amount` and `bookings.currency` are not in the SELECT list at all; the `revenue_month` stat key is absent. Row-level amounts count as revenue.
- "Revenue this month" uses the IST calendar month (the business runs on IST); captured bookings only, summed per currency.
- "Total" bookings excludes `cancelled` and `refunded`. "Brief missing" counts captured bookings with no `brief_submitted_at`.
- The client's own timezone is only known when they filed a slot request (`requester_timezone`); otherwise the Bookings table shows IST plus the viewer's local zone, labelled as such.
- "Email booking link" sends `/confirmed?razorpay_payment_id=<id>` (Razorpay's own redirect parameter) and sets `reminder_sent_at`, so the 6-hourly cron does not send a duplicate.
- Slot-request approve: claims the request (`status=pending` → `approved`) first as a lock against double approval, then sets the booking; the DB's partial unique index on `slot_start` turns a clash into a clean `409 slot_taken` and the request is reverted to pending. Then calls the site's `create-meeting` with `{ booking_id }` and sends both confirmation emails from the admin function. If the site's create-meeting also emails, one of the two must stop — noted in DEPLOY.md.
- Decline emails the next 12 open slots, computed by the same generator the Availability preview uses, in the client's zone and IST.
- Weekday numbering in `availability_rules`: 0 = Sunday … 6 = Saturday (JavaScript `getUTCDay`).
- Slot overrides are interpreted in the `scheduler_timezone` setting (default Asia/Kolkata), since `slot_overrides` has no timezone column.
- Team: an owner also cannot deactivate themselves (in addition to not changing their own role). After a demotion/deactivation of an owner the function re-counts active owners and undoes its own write if a concurrent change left none.
- Deactivation also bans the auth user via GoTrue (`ban_duration`) as defence in depth; reactivation lifts it. Rows are never deleted.
- Inviting an address that already has an auth account (but no team row) links that account and sends a magic link instead of failing.
- Content: only existing `site_content` keys can be edited (no create, no delete); empty values are refused so the site can never build with empty copy.
- Answers: no delete action — unpublish instead. Any change to an answer that is or was published triggers a rebuild. One audit row per save listing the changed fields.
- Signals: `session_id` is never selected. Traffic returns aggregates only.
- Hard deletes are allowed by the data layer on exactly two tables: `slot_overrides` and `availability_rules`. Everything else, including `team_members`, is refused in code.
- `trigger-publish` lives in this repo (it is only ever called by the admin). repository_dispatch returns no run id, so the function looks up the run created after the dispatch and the UI polls it.
- site_settings keys (the site repo must read the same names): `razorpay_mode` (`test`|`live`), `razorpay_payment_url_test`, `razorpay_payment_url_live` (each a Razorpay Payment Page URL, or blank — renamed from `razorpay_button_id_*` to match the site repo), `scheduler_timezone`, `scheduler_slot_minutes`, `scheduler_buffer_minutes`, `scheduler_min_notice_hours`, `scheduler_window_days`. Two payment page URLs + a mode key means switching Test↔Live is one change and one audit line, and the other URL is never lost. The weekly windows stay in `availability_rules` (§8 pane 3); "the scheduler's availability rules" in site_settings is read as the scheduler's parameters.
- site_settings `value` is assumed to be `text`; numbers are stored as their decimal string. If the column is jsonb, the stored values become JSON strings — see DEPLOY.md.
- Cross-key rule: the mode can only point at a payment page URL that is set, and the active URL cannot be blanked.
- Settings has "Save & Publish" as well as "Save", because if the site reads site_settings at build time a change only goes live on the next build. Owner and admin can both use it (both hold publish rights in §9).
- The settings validator is one plain-JS file enforced by the Edge Function; `build.py` keeps a byte-identical copy at `public/js/shared/` for the browser and `check.py` fails if they drift.
- Magic-link sessions use GoTrue's implicit flow (tokens in the URL fragment, stripped on arrival) and live in localStorage; refresh via `/auth/v1/token?grant_type=refresh_token`. The sign-in form always replies "If that address is authorised, a sign-in link is on its way."
- Routing is by hash (`#/bookings`), so Cloudflare needs no SPA rewrite and `_redirects` is not shipped. A pane the role cannot see is never mounted even if typed into the address bar.
- CSP has no `unsafe-inline`: no inline scripts, styles or style attributes anywhere (check.py enforces). Chart and rank bars are SVG attributes for that reason.
- The Traffic chart is a single-series bar chart in one accent colour, with per-bar hover titles and a table view. Days are IST calendar days.
- The PUBLISH button is the one filled-gradient control in the admin; everything else is outlined (mirrors the site's convention).
- Display times: IST first, then the client's zone (if known) or the viewer's own zone when it differs from IST.
- Native `confirm()` dialogs guard every outward action (emails, approvals, role changes, deactivation, publish, Live mode).
- Email domain lock: the GoTrue user's email is checked before team_members is read, and the team row's email is checked too (defence in depth). Exact domain only — subdomains and lookalikes are refused. Comparison is case-insensitive. `ALLOWED_EMAIL_DOMAIN` accepts `example.com` or `@example.com`; blank means the default.
- The domain constant is a plain-JS shared module (like the settings validator) so the browser imports a byte-identical copy; build.py writes `ALLOWED_EMAIL_DOMAIN` into config.js (null → the module's default), so the literal exists once.
- Team invite also refuses off-domain addresses (400 with the required domain named) — such a member could never sign in. That message is shown only to an owner, so it reveals nothing to an outsider.
- The sign-in page answers an off-domain address with "Use your @avidproblemsolvers.com address." This states a public policy, not whether an account exists; on-domain addresses still all get the one neutral reply.
- Payment page URL validation is one anchored regex over the whole string, not a URL parser, so there is no parser normalisation to exploit. Beyond the brief: bare `razorpay.com` is rejected (only subdomains); query strings and fragments are rejected (path characters only — Payment Page links need neither); percent-encoding is rejected (unreserved characters and `/` only); the path must contain at least one non-slash character (`https://rzp.io/` alone is refused); scheme and host must be lowercase, as Razorpay issues them. Surrounding whitespace is trimmed before validating and storing.
- Old `razorpay_button_id_*` keys are now unknown to the schema and refused on save. Any rows already stored under those names are left alone (this repo never deletes site_settings rows) and simply no longer shown.
- Sign-in uses a six-digit emailed code (`/verify`, type "email") because Zoho's scanner spends single-use links. The code field appears for every on-domain address after a send, so its presence reveals nothing; off-domain addresses get the domain message and no field.
- One message ("That code did not work. Check it, or request a new one.") for wrong, expired, spent and unknown-address codes, and for any non-session reply. A malformed code (not six digits) is refused locally with "Enter the six-digit code from the email." without a request.
- After a send, the email form stays above the code field (address prefilled) so the user can correct it or request another code; its button is disabled for 30 s as before. The code form carries the address in a hidden field so verification uses exactly the address the code was sent to.
- The verify button is the primary control once a code is requested; "Email me a sign-in code" drops to outlined.
- `create_user: false` is kept on `/otp`; `/verify` cannot create accounts. The emailed template change (code instead of link) is a dashboard step for the user — DEPLOY.md §1.
- Light theme pre-paint script is an external classic script (`/js/theme-init.js`) in `<head>`, not inline: the CSP has no `unsafe-inline` and build config was out of scope. Being parser-blocking it still runs before `<body>` is created, so there is no flash (smoke test asserts this).
- Colour tokens are named by role; `#7FE9E1` splits into `--accent-fg` (text), `--accent-hi` (gradient end, hover fill), `--focus` and `--ok`, and `#07211F` into `--bg` and `--on-accent`, because those roles need different light values. Non-colour constants (`--ease`, `--t`, fonts, `--r`) moved to an `html {}` block so `:root` holds only themed colours.
- `transparent` and `currentColor` are keywords, not palette colours, and are allowed in rules.
- The light theme adds colours beyond the CLAUDE.md palette (darkened teal, amber and coral for contrast on near-white); check.py still pins the dark `:root` block to the CLAUDE.md palette.
- The "Admin" eyebrow in the header is hidden below 400px so the theme toggle fits on the narrowest phones.
- The logo PNG is unchanged in light mode (rule 1); it keeps its own dark-teal background.
- Content sections: tab and heading order is plain code-point order of the raw segment (so `ANSWERS_INDEX` sorts before `answers_index`); fields within a level likewise by key.
- A key that is also a prefix of others (`a.b` and `a.b.c`) shows `a.b` as a field at its own level and `a.b.c` under a "B" heading — both kept, nothing merged.
- A single-segment key (`solo`) gets its own tab "Solo" holding one field "Solo".
- Content section lives in the hash as `#/content/<segment>` (URI-encoded). An unknown or empty section falls back to the first tab without rewriting the hash.
- While a content search is active no section tab is marked current; clicking a tab or a hit's path clears the search and opens that section.
- Section tabs show the key count and, in warn colour, the number of unsaved edits in that section (edits are pane-wide, so they would otherwise be invisible from another tab).
- Headings use role="heading" with aria-level = depth + 2 (unbounded) rather than h3–h6, so depth beyond four still has a correct level.
- Measuring used Chrome over the DevTools protocol (as browser_smoke.mjs does), not Playwright: Playwright is not a project dependency and the only installs on this machine are outside this folder.
- Mock seed gained answers_index.* keys up to six segments deep, so the nesting is visible locally.
- Pane cache: in memory only (never localStorage — it holds booking and team data), keyed by pane id, holding the load made with the pane's default filters. Filtered reloads are not cached.
- Pane cache freshness is 30 s: a revisit inside that makes no request; after it the cached data paints at once and one background request refreshes it. The refresh repaints only if the data changed and the user has not interacted with or focused anything in the pane, so it never clobbers typing.
- Any non-read action (anything outside list/get/summary/detail/status/export_csv) clears every pane's cache, not just its own: writes have cross-pane effects (approval → booking + audit row; any write → audit).
- No skeleton screen and no fetch parallelisation: measured first paint is already ~10 ms and every pane makes exactly one call, so neither moves a number.
- First-visit time is the Edge Function round trip plus cold start and cannot be fixed in the browser. Options (keep-warm pings, or consolidating the ten admin functions so one cold start serves all tabs) are server changes left to the owner.
- Content groups: "lowest-level group" is read as every heading's (and every section's) OWN fields — a heading with both fields and sub-headings gets a textarea for its fields, then its sub-headings below.
- Group textarea parsing: the label is trimmed and must match exactly (case-sensitive); one space after the colon is dropped, any further spaces belong to the value; a missing space is tolerated; blank lines are ignored; line order may change. A line with no colon is an error, as is a value emptied (the server refuses empty copy anyway).
- Besides values with line breaks, two more cases cannot round-trip and are edited on their own, with the reason shown: a label containing a colon, and two fields in one group whose segments humanise to the same label (e.g. `min_chars` and `MIN_CHARS`).
- An invalid group holds only its own keys: Save still sends other groups' edits, keeps the typed text (marked invalid, errors above it), and the toast says which did not save. A group that turns invalid drops its earlier valid edits too, so nothing half-typed is ever sent.
- Group textareas use Plex Mono so label/value columns read cleanly; standalone fields keep Inter.
- Auto-height: CSS `field-sizing: content` plus a JS fit (`view.after` hook in pane.js, called after every paint) for browsers without it. Setting `.style.height` is CSSOM, which the CSP allows.
- sort_order is read via the existing `select *` and ordered in the browser; the query never names it, so an unmigrated database keeps working. A group or section takes the lowest sort_order of any field beneath it, at any depth.
- Nav weight: both tab rows at 600 (Plex Mono 600 added to the font request); active tab keeps its accent colour and underline. Counts in section tabs stay at 400 so the label carries the weight.
